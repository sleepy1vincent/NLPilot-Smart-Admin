## 10-29 · 协议统一与清理

**做了什么**
- `recognize` 返回改成**固定 6 字段**：`ok / kind / tool / args / message / recovered`
- 下游三个消费方改成 switch `kind`
- 删除死代码：`product_service` 的 `is_txt` 分支、`sales_report` 的 `total_quantity` 别名、两个路由的未使用导入
- 把 `guard_service` 接回真实调用点（之前被绕过了）
- `trace` + `results` **合并成一条 `steps`**（前三个字段完全重复）
- 前端跟着改：`data.results` → `data.steps.filter(s => s.result)`

**为什么**
- 四种返回形状让每个调用方都要猜结构；两条平行数组让"一步"的信息分裂在两处

**A/B 实验（写回灌格式）**

| 写法 | 多步 | 结论 |
|---|---|---|
| 标准：`assistant(tool_calls)` + `tool` | **5/5** | 采用 |
| 只发 `assistant` 一条 | 3/5 | 模型以为"已答完"，收尾 |
| 只发 `tool` 一条 | 5/5 但参数易丢 | 违反"tool 必须跟在 tool_calls 之后"的契约 |

## 10-30 · clarify 泛化 + 失败语料

**做了什么**
- `clarify(field=枚举6选1)` → **`clarify(slots=任意名词短语)`**
  - 校验：最多 4 个槽位 / 每个 ≤ 12 字 / 禁止句子标点
  - 不合格 → 退回 FALLBACK，绝不展示半句话
  - 渲染：`请补充：促销商品 / 目标人群 / 预算`
- 新增 `docs/failures.md`：16 条真实失败记录（含触发语句、当时行为、修法）
- 修评测脚手架：dry-run 的返回文案曾写成"未真正执行"，**被模型当成失败信号**，
  导致 6 条写操作用例误判 → 改成与真实成功同形
- 各文件头统一"返回协议 + 历史备注"的写法

**为什么**
- 六选一的 `field` 装不下"促销计划缺什么"，模型只能退回自由文字，而自由文字会被重试掰弯

**当天发现的两个新问题**
- 开放式 `clarify` 会被滥用：模型查完数据还追问"您想查哪个商品"（`slots="缺什么"`）
  → 已加规则：**已执行过工具时，clarify 一律忽略**
- 多步总结会编造细节（如 `-sale-record-id: 12345`）→ 未解决

## 怎么用这份记录

1. **答辩/面试**：按上面 6 个节点讲，每个节点都有"做了什么 → 为什么 → 数据"
2. **写 README**：这里的"为什么"可以直接搬
3. **复盘**：每次改完看一眼"未解决"，避免又回到已解决的问题上

> 注：完整评测（`tests/agent_eval.py`，32 条）跑一次约 1~2 分钟，只在**大改动后**跑；
> 日常小改用"3 条快速自检"（导入 + 语法 + 一两个典型问法）即可。
