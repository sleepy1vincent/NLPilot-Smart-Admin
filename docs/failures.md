# 失败记录（评测语料）

这里记录**开发过程中真实发生过**的失败，每条都可以直接变成一个评测用例。
原则：只记实际观测到的，不记"可能会发生"的。

字段说明：
- **触发**：用户的原始输入（可直接当评测的输入）
- **当时行为**：系统实际输出了什么（错在哪）
- **期望行为**：正确答案
- **状态**：已解决 / 部分缓解 / 未解决

---

## A. 幻觉类

### A1 模仿上文的格式，编造库里不存在的商品

- **触发**：`第一次见对象带什么合适` / `便宜实惠性价比高的`
- **当时行为**：输出「共 3 条：· 华为MateBook D15 ¥4299 库存67 · AirPods Pro · 小米手环7 ¥249」——
  这三个商品**库里都不存在**（真实的是 联想小新Pro14 / AirPodsPro / 小米手环8）
- **原因**：模型没调工具，但模仿了历史里"结果卡片"的排版，自己造了一份
- **期望行为**：不调工具就不许输出商品清单
- **解决**：`executed == 0` 时**丢弃模型文字**，换固定兜底话术（`agent_service._no_tool_text`）
- **状态**：✅ 已解决（结构上不可能）

### A2 把「销量」当成「库存」

- **触发**：`这周卖得最好的商品还有多少库存`
- **当时行为**：`sales_report` 返回销量 5，模型回答"iPhone15 还有 **5** 个库存"（实际 138）
- **原因**：两种数字语义相近，模型混用了
- **期望行为**：先 `sales_report` 找商品，再 `query_products` 查库存（2 步）
- **解决**：① `sales_report` 返回字段改名 `sold_quantity` + message 明写"这是销量，不含库存"；
  ② prompt 加"问库存必须另调 query_products"
- **状态**：✅ 已解决（实测变成 2 步链式调用）

### A3 库存充足却建议"补货"（语义反向）

- **触发**：`给点补货的意见`
- **当时行为**：
  「安克充电器库存还有 120 个、充电宝库存 300 个 → **建议及时补货**」
  「iPhone15 库存 235、iPhone17 库存 200 → **建议补 iPhone17**」
- **原因**：只有库存数字，**没有任何销量/周转信息**，模型自己编了个"库存少=该补"的规则
- **期望行为**：有销量数据才给补货结论；没有就说"需要销量数据"
- **解决**：① `_enrich()` 在单商品查询时补 `daily_sold` / `days_left`；
  ② 新增 `discount_candidates`，把"该打折/该补"的排序交给代码算
- **状态**：✅ 已解决（实测「促销iphone 预算500」→ `discount_candidates`，按周转给结论，不再拿预算当价格筛）

### A4 换算错 30 倍

- **触发**：`小米手环8 最近30天卖了多少，库存还剩多少，可售几天？`
- **当时行为**：拿到 `sold=6`（30天）、`stock=194`，算出
  "以每天卖出 **6** 个的速度，可售 **32.33** 天"
- **期望行为**：日均 = 6/30 = 0.2 → 可售 = 194/0.2 = **970 天**
- **原因**：模型把"30 天总销量"当成"日销量"，量纲错误
- **解决**：同 A3，派生指标由代码算好再给模型
- **状态**：✅ 已解决（实测回答"每天约 0.2 个，还能卖 970 天"）

## B. 工具调用类

### B1 把「售出 N 件」理解成查询，而不是记录

- **触发**：`AirPodsPro 售出 3 件` / `卖了 2 个 iPhone15`
- **当时行为**：选 `query_products` 或 `sales_report`，不选 `record_sale`
- **期望行为**：`record_sale(product_name=..., quantity=...)`
- **状态**：🟡 部分缓解（单步 21/21，循环约 20/21，属偶发）

### B2 把 tool_call 写成普通文本（4 种形态）

- **触发**：多种
- **当时行为**：模型不通过 `tool_calls` 字段返回，而是把调用写进 `content`：
  1. `{"name": "query_products", "arguments": {...}}`
  2. `clarify(field=chat)`
  3. `recommend_products({"occasion": "钓鱼"})`
  4. `record_sale(product_name="iPhone15", quantity=2)` ← 多个关键字参数
- **期望行为**：正常走 `tool_calls`
- **解决**：`_recover_tool_call()` 四种形态全部可解析，并用 `_coerce()` 还原参数类型
- **状态**：✅ 已解决（但属"模型怪癖"，需长期观察）

### B3 参数缺失

- **触发**：`500 以内有什么`
- **当时行为**：`max_price=None`（模型知道要筛价格，但没把 500 填进去）
- **状态**：🟡 偶发（只在简化回灌格式时稳定出现）

## C. 多步类

### C1 多步只保留最后一次结果

- **触发**：`查 iPhone15 的库存，再查 AirPodsPro 的库存`
- **当时行为**：走了 2 步，但 `result` 只保留第 2 步，**iPhone15 的数据被覆盖**
- **期望行为**：两步的数据都要给用户
- **解决**：返回 `steps` 列表，每条带自己的 `result`；前端逐条渲染卡片
- **状态**：✅ 已解决

### C2 写完就停，把"两件事"做成一件

- **触发**：`创建一个商品名为测试品的商品，然后给我看看什么适合送给领导`
- **当时行为**：`create_product` 成功后循环立刻结束，推荐没做
- **解决**：改成「写预算」——写完不结束循环，只禁止第二次写
- **状态**：✅ 已解决

### C3 并列商品名查不到

- **触发**：`查一下小米手环8 和 罗技鼠标M590 的库存`
- **当时行为**：模型传 `name="小米手环8,罗技鼠标M590"`（整串当一个名字）+ `in_stock=True`
  → 单条 LIKE 必然 0 条
- **期望行为**：返回两个商品
- **解决**：`query_products` 里按分隔符拆名，各带同样筛选条件分别查、按 id 合并
- **状态**：✅ 已解决

### C4 名次类问题数错

- **触发**：`第二贵的商品是什么` / `价格第四高的是什么`
- **当时行为**：拿 `rank=1` 说成"第二贵"，拿 `rank=3` 说成"第四高"
  （实测 N=1、N=3 对，N=2、N=4 错）
- **尝试过但无效**：① 只加 `sort` ② 每条加 `rank` 字段 ③ 把名次写进 message 句子
- **解决**：加 `nth` 参数，由 SQL 的 `OFFSET` 直接取第 N 条，模型不做算术
- **状态**：✅ 已解决（4/4 全对）

### C5 步数用尽后输出英文 + 截断

- **触发**：`给个促销计划`
- **当时行为**：第 3 步（应输出计划）输出了
  `ronics sold in the last 7 days total 10 items across 4 orders...`——英文、截断、重复两次
- **原因**：3 步的观察（每步最多 2000 字符）+ 历史，上下文过长，7B 输出退化
- **状态**：❌ 未解决。修法：把 `_shrink` 调回中间值（约 1200 字符 / 6 条）+ `reply` 截断

### C6 合理的澄清被"重试"掰成擅自行动

- **触发**：`给个促销计划`
- **当时行为**：第 1 次它说"我需要知道促销哪个商品、目标人群、预算"（**这是对的**），
  但因为 `retry_text=True`，被重试一次后变成直接 `query_products(in_stock=True)`
- **原因**：`clarify` 的槽位是封闭枚举（name/quantity/price/stock/target/which_one），
  装不下"促销目标/人群/预算"，模型只能退回自由文字，而自由文字会被重试
- **状态**：❌ 未解决。修法：把 `clarify` 改成"可填任意槽位名"（见 `reply_templates`）

## D. 对话类

### D1 闲聊被重试掰成"查全部商品"

- **触发**：`在吗` / `你好` / `你是谁` / `讲个笑话`
- **当时行为**：拉出 27 条商品，回复"这里有几款商品供您选择：1. iPhone15…"
- **原因**：`recognize` 里"文字回复再试一次"的逻辑，第二次被 nudge 逼成 `query_products()`
- **解决**：单步模式不重试文字（`retry_text=False`）；循环模式重试，但 nudge 改成中性措辞
- **状态**：✅ 已解决（闲聊 5/5 正常）

### D2 空响应（模型什么都不返回）

- **触发**：`有哪些耳机`
- **当时行为**：`content=''`、`tool_calls=None`，但 `eval_count=16`（生成了 16 token 又被丢弃）
- **原因**：ollama 对某些 tool_call 生成结果的解析缺陷（6 个 seed 全部复现）
- **解决**：空响应算失败 → 给最后一条 user 消息补一句提示再试，实测能恢复
- **状态**：✅ 已解决

### D3 模型原文漏到界面

- **触发**：任意（尤其闲聊）
- **当时行为**：模型随口说的话直接显示给用户，可能夹带"已删除""库存 5"等
- **解决**：模型只能说 `clarify` / `refuse` 的枚举值，句子由 `reply_templates` 渲染；
  `executed == 0` 时模型文字一律丢弃
- **状态**：✅ 已解决

## E. 多轮与追问类

### E1 用户把决策权交回来时，系统只会兜底

- **触发**（真实对话，2026-10-30）：
  ```
  用户：给我制作一个促销计划
  助手：请补充：促销商品 / 目标人群 / 预算        ✅
  用户：目标人群是学生
  助手：请补充：促销商品 / 预算                  ✅（记得住已答的内容）
  用户：这些你给我补充不行吗
  助手：我没能理解这个请求。你可以这样说：…        ❌
  ```
- **当时行为**：连续两轮 `clarify` 之后，用户说"你替我定"，系统直接兜底
- **原因**（三条叠加）：
  1. prompt 里**删掉了**"用户说'你定'时你自己生成合理的值"这条规则（砍自由对话那轮一起删的）
  2. 没有工具能表达"好的，我来定"——`clarify` 是"问用户"，`refuse` 是"做不到"，中间那档空缺
  3. 模型于是吐了文字 → `executed == 0` → 按规则被丢弃 → 兜底话术
- **期望行为**：接受授权，自己查数据（库存/销量）挑一个方案；如果确实做不到，就 `refuse(out_of_scope)`
- **状态**：❌ 未解决
- **候选修法**（明天选一个）：
  - A. 让模型直接调业务工具自己拿主意（无需新工具，但要恢复"你定"规则）
  - B. 加一个 `propose_plan` 类工具，让"我来定"有结构化出口
  - C. 明确 `refuse(out_of_scope)`，不假装能做

### E2 clarify 的字段名在两处不一致（参数时好时坏）

- **触发**：`帮我删了` 等需要反问的场景
- **当时行为**：`recognize` 返回 `args = {'field': '商品名'}`，但函数签名是 `slots`
  → `args.get("slots")` 拿到空 → 退回兜底。**同一个问题，有时能问、有时不能**
- **原因**：`tools.clarify(slots=...)` 已改，但 `system_prompt.py` 里仍写着 `clarify(field=...)`，
  模型拿到两套互相矛盾的说明
- **解决**：prompt 改成 `clarify(slots=...)：把缺的名词写进去，逗号分隔`
- **状态**：✅ 已解决

### E3 两个 `kind` 撞名

- **现象**：`recognize()` 的 `kind` 是 `"tool"|"text"|"error"`；
  `tools.clarify()` 返回的 `kind` 是 `"clarify"`。同一个词，两层含义
- **影响**：读代码时必须先判断"这是哪一层的 kind"，容易误判
- **核实**：`tools.clarify/refuse` 返回里的 `kind` **没有任何地方读取**
  （这两类调用在 `product_service.handle` 之前就被拦下了）
- **解决**：删掉 `clarify` / `refuse` 返回里的 `kind`，现在项目里 `kind` 只有一种含义
- **状态**：✅ 已解决

### E4 改 prompt 大段落 → 全线退化（教训）

- **过程**：为了修"顾客侧/管理侧混用"，一次性往 prompt 加了 4 个新段落
  （顾客侧vs管理侧、查询要带过滤、你定规则、总结别重复）
- **结果**：工具选择 **21/21 → 14/21**，写操作全部被误判成 `query_products`
- **回退**：只保留 `clarify(slots=)` 这一处必要修改 → 回到 **21/21**
- **教训**：**7B 的 prompt 改动只能一行一行加，每加一行都要回归。**
  一次加四段 = 无法定位是哪一段坏的。

## 怎么用这份清单

1. **每加一个评测用例**，从上面挑一条"触发"原句直接填进去
2. **修完一条**，把"状态"改成 ✅ 并写清修法（这是面试/答辩最值钱的部分）
3. **改代码前先跑** `python tests/agent_eval.py`，改完再跑，数字不许变差
   （注：完整评测较慢，日常小改用 5 条快速自检即可）
